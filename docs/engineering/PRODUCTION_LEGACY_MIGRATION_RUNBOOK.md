# Legacy PostgreSQL migration: rehearsal and release gate

This is not an approved production procedure. The isolated copy tool preserves the source and checks six caller-supplied migration records, shared table contents using multiset equality, and opaque audio bytes. Exact fixture hashes must be independently matched against the approved release artifacts; six caller-supplied entries alone do not establish provenance. It refuses all outstanding provider leases. Do not run against production without approval of the exact release and plan.

For rehearsal only, set `VIVA_POSTGRES_TEST_DSN` to a dedicated disposable database, then from `implementation` run `python -m pytest backend/tests/integration/test_postgres_legacy_upgrade.py -q`. The tests create and delete disposable schemas. Never point them at production.

`frozen_legacy_schema` holds write-conflicting locks on all existing legacy tables for the lifetime of a PostgreSQL transaction. Pass its connection to `copy_legacy_schema(..., frozen_connection=connection)`; an exception before exit rolls back the copy, and database disconnect also releases the locks. Competing legacy writes fail or wait. The locks are not a traffic switch, do not prevent new tables or privileged schema changes, and end when the transaction commits. The copied data is invisible to other connections until commit, so this mechanism alone cannot provide an atomic externally visible cutover. A separate independently enforced application/traffic freeze must continue across commit, integrity verification, routing changes, and activation of the target. The operator must verify no bypass writers, background jobs, leases, or cleanup obligations remain. No production freeze or migration has been performed.

Before any approved cutover, independently verify exact historical checksums, inventory all source tables and functions, stop admission and drain active sessions and leases, enforce and verify the external freeze, preserve a restorable checkpoint, perform the copy under locks, and verify source and destination counts and multiset equality. Verify ownership, foreign keys, ordering, audio playback, quota and cleanup state before allowing target writes. Maintain the freeze until the verified release is routed correctly. Recheck migration history and live data immediately before execution.

If interrupted before commit, the transaction rolls back and may be retried after the external freeze and source state are revalidated. If target writes have begun, do not route back to the legacy application: reverse reconciliation and lossless rollback are not implemented. Preserve both schemas and logs and keep writes stopped while engineering assesses forward recovery; no automated forward recovery or post-write losslessness is demonstrated. A pre-cutover backup does not preserve later target writes.

Release blockers: no tested cross-system freeze/cutover orchestration, tie-ordering acceptance, serving of retained legacy audio, post-write recovery, or comprehensive live-state reconciliation exists. The tool is a rehearsal component and must not be represented as production-ready.

## Additional disposable fence and restart evidence

`legacy_fence.install_legacy_fence` is an experimental transactional DDL primitive: it locks existing tables, installs persistent statement triggers rejecting insert, update, delete and truncate, and commits the triggers together. The disposable suite verifies those operations fail for a restricted non-owner role after commit, rejects a superuser role, and verifies failed installation rolls back and can be retried. It checks only the named role and current tables. It does not verify all production credentials, role changes, all privileged session settings, future objects, replication paths, or external system writes. An owner or superuser can disable/remove triggers; do not use this as a production fence with shared owner credentials. This installation itself changes source-schema metadata and requires explicit production approval. No production DDL was performed.

A separate disposable test restarts the same new-schema artifact after one post-copy workspace write and confirms that row and copied audio remain. This is only an idempotent initialization and data-preservation check, not proof that a previous release artifact is compatible, that all post-cutover data is preserved, or that an interrupted application failure can be recovered. A separately identified, reviewed compatible artifact and comprehensive forward-recovery rehearsal remain required. The old-schema app is not a safe rollback after target writes.

## Forward-only runtime recovery rehearsal

A disposable PostgreSQL rehearsal creates the current v100/v101 schema, records synthetic coding source and revision, completed learning progress, workspace recovery credentials, a codebase conversation, a valid silent WAV, and synthetic committed provider accounting. It shuts down one application instance, starts a separate application instance in the same test process using the same local code and settings, and compares row counts and SHA-256 hashes of the complete row multisets for every ordinary table before issuing recovery-instance reads. It then verifies the records, audio bytes, coding revision and workspace credential recovery through HTTP. Reads and recovery requests can legitimately change admission and credential records, so the full-table comparison precedes them. Audio and provider ledger rows are seeded locally; no provider is contacted. This is a local same-code restart test, not a deployed artifact, an arbitrary code-fix test, or proof of post-write rollback. Re-run against the exact approved release and record its commit and schema checksums before relying on it.

The isolated role test grants a synthetic staging role access to the target schema and verifies that it cannot read or insert in the separate legacy-shaped schema. This does not establish that real preview credentials are restricted: verify the actual database role, inherited memberships, schema privileges, default privileges and connection target before staging. The trigger fence above still cannot protect against an owner, superuser, new tables or unexamined writers.

For an approved forward-only incident response after target writes: stop admission and writes, retain the target schema and all logs, verify the running writer processes are stopped or isolated, and preserve outstanding provider reservations and unknown outcomes. Confirm the chosen recovery artifact's identity, reviewed schema compatibility and migration checksums. Start that compatible artifact against the existing target schema without re-copying or reinitializing data; compare available integrity evidence, then verify ownership, recovery, sessions, source, conversation, audio, quotas and outstanding work before reopening traffic. A provider call past the dispatch marker may still reach the provider after database fencing; confirm the old worker has stopped and reconcile externally before resolving unknown usage. If the same artifact has a code defect, restart alone does not repair it: a separately reviewed, schema-compatible fix and its own rehearsal are required. Never route the old-schema application to the new schema or claim a lossless downgrade; reverse reconciliation is not implemented. These steps remain a proposed operational procedure until rehearsed with the exact deployment and real platform controls.

Run locally only against a dedicated disposable database: `VIVA_POSTGRES_TEST_DSN=<disposable-dsn> PYTHONPATH=implementation/backend:implementation <python> -m pytest implementation/backend/tests/integration/test_postgres_forward_recovery.py implementation/backend/tests/integration/test_postgres_legacy_upgrade.py -q`. These tests create and drop schemas and roles and must never target production.
