# Zero-cost deployment plan

Status: design and audit only; no production services provisioned. Free usage and entitlement must be verified in the actual accounts before use. No paid billing, trial with payment details, or automatic charges are authorized.

## Target and decisions still requiring proof

Use Vercel Hobby for the existing React frontend and, if feasible for this application, request-driven FastAPI endpoints. Use Supabase Free PostgreSQL as the durable source of truth, with server-side credentials only and carefully enforced session ownership. Investigate Vercel Sandbox for each disposable untrusted Python invocation; keep trusted oracles, credentials and verification outside it. Preserve the existing gVisor adapter. Vercel now documents WebSocket Functions as generally available, including FastAPI on Fluid Compute; determine actual Python/runtime support, connection duration and account eligibility by testing before choosing it or an authenticated, tightly limited Render Free bridge. Both transports remain product requirements. Public code execution remains disabled until actual isolation acceptance passes.

Run the complete live acceptance suite and record measured usage, no mock substitutions. Roll back or keep execution disabled if a gate fails.

## Free-tier limitations

A free allowance is a ceiling, not proof that the full demonstration will fit. Estimate execution minutes, CPU/memory, database size and egress, speech seconds and provider credits before load; record actual account quotas and usage as measured. Hobby Sandbox documentation says creation pauses on quota exhaustion, but account-specific access and all other product behaviors require verification. No recurring scheduler, streaming runtime, external service, domain or paid plan is assumed free without checking its current terms.

## Sandbox design investigation — unresolved controls

The requested replacement is authorized, but it must meet the existing security requirements. Vercel documents a Firecracker microVM and a Python Sandbox SDK, a different trust boundary from the current runsc worker. A staged design would create one nonpersistent deny-all sandbox per invocation, inject no app credentials or ports, stage only the learner runner and one input, enforce wall and command deadlines, compare independently outside the VM, and record sandbox IDs durably for cleanup and reconciliation. Bind acceptance to the exact deployed configuration and run real adversarial tests before enabling custom code.

The existing worker additionally relies on per-job 256 MB memory, PID cap, read-only root, no-new-privileges, capability restrictions and bounded tmpfs. Official documentation reviewed so far does not establish equivalent guest-independent per-job limits on Vercel Sandbox; the documented memory allocation is tied to vCPUs and the guest user has sudo. Vercel's own [untrusted Python guidance](https://vercel.com/i/run-untrusted-python-code) cautions that retained output limits do not by themselves bound remote output, incoming traffic or SDK memory. Process rlimits inside a guest controlled by untrusted code cannot substitute for an external boundary. Treat the adapter as blocked pending proof or a genuinely free alternative that meets the full controls; no mock adapter is evidence of safety.

## Fresh Sandbox feasibility observation, 15 November

A fixed inspection on the actual Hobby account found writable cgroup v2 controllers and a successful privileged mount/PID/network namespace creation. The disposable VM was deleted afterward. This makes a trusted supervisor with an unprivileged child, external child cgroup limits, private read-only mounts, bounded output pipes and complete process-tree termination a candidate for investigation. It does not establish those controls: no learner runner or limit acceptance was implemented or exercised. The provider VM still provisions 2,048 MB for one vCPU, above the existing 256 MB invocation policy; direct SDK resource selection does not preserve that policy. A safe runner must prove enforcement against the child and prevent it from changing or bypassing the supervisor's controls. The earlier lack of SDK-level controls should not be presented as proof that this supervised design is impossible.

## PostgreSQL migration boundaries

At inspection, 26 application Python files directly reference SQLite connections. Existing migration 0008 uses FTS5, while other migrations use SQLite triggers, JSON functions, and SQLite-specific transactions. Preserve original migration checksums and add a separately tracked PostgreSQL migration series; do not translate SQL by replacing placeholders. Add a pinned driver, TLS-verified secret URL, separate migration/runtime privileges, PostgreSQL-specific readiness and backup procedures, and a lock-protected migration runner.

Port all modules together before switching the application: sessions, immutable code and evidence, ownership and capability revocation, Studio, learning, interviews, repository learning/search, speech usage, admission and deletion. Replace `BEGIN IMMEDIATE` serialization with explicit shared row/advisory locking in all paths that reserve and settle quotas or race with deletion. Keep provider calls outside transactions, conserve uncertain reservations after crashes, and never blindly retry an external call. Include privacy aggregate/cascade behavior from migrations 0023 and 0024. Test CAS, simultaneous admissions, idempotency, delete/publication races, migration rollback/checksums and crash recovery against real PostgreSQL before cutover. A PostgreSQL connection foundation alone must reject runtime selection until all repositories are ported; do not silently split product state across SQLite and PostgreSQL.

## Alternatives investigated

No hosted alternative was verified to satisfy all required no-card, no-automatic-charge, no-network, hard resource, isolation and cleanup controls. GitHub Actions is not a suitable request-serving execution backend under its [additional product terms](https://docs.github.com/en/site-policy/github-terms/github-terms-for-additional-products-and-features); Oracle's [Always Free signup](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier.htm) generally requires a card. A user-owned, always-on Linux machine could run the existing gVisor worker without a cloud subscription, but hardware/electricity, safe connectivity, durable recovery and real adversarial acceptance would still need verification. It has not been supplied or tested here.
