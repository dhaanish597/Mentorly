## Current integration facts and recommended boundary

`/api/v1/sessions` creates DSA sessions; existing session-specific endpoints and security assume `sessions.id`, a required `exercise_id`, `spec_version`, `active_code_version_id`, DSA `RevisionRef`, and code-version/turn foreign keys. `session_security` authenticates `Authorization: Bearer` against a SHA-256 token hash, requires `X-Idempotency-Key` on mutations, bounds request bodies, and stores replay records; its route regex only covers `/api/v1/sessions/{id}`. Its per-key asyncio lock is process-local. SQLite replay is durable but the check/save and handler effect are not one atomic transaction, so it is not a general multi-process exactly-once guarantee. Admission recognizes only the same DSA route and creation path; it uses durable fixed-window counters but process-local inflight capacity. Existing retention enumerates only `sessions`, tombstones and uses durable cleanup obligations; speech service reads DSA revision and source hash, and gatekeeper's usage tables reference `sessions(id)` (its placeholder-session support must never be used for new modes). Existing `session_events` are DSA-owned; TTS streaming exists, but durable resumable general-purpose event streaming is not established.

Recommend a separate `studio_sessions` aggregate and `/api/v1/studio/sessions` API for the five new non-DSA modes. Leave current DSA paths and tables behaviorally intact and expose one frontend studio abstraction. This deliberately deviates from the plan's proposed polymorphic `/sessions` body and `sessions` alterations because current schema and security depend on mandatory DSA fields. Document this compatibility mapping in OpenAPI; do not claim the original endpoint supports new modes. A future unified facade may dispatch by discriminator, but only after backward compatibility, authorization and no-dummy-record tests. The public UI still offers all six modes. Share utilities and provider transport, not DSA state machines or fake code rows.

Migration 0006 is `0006_typed_predictions.sql`; verify next available version before adding (currently 0007). The supplied SQL uses incompatible identifiers and must be adapted to actual schema and migration checksums, not copied verbatim. Back up online before migration, test populated 0006 upgrade and restore, retain historical data and enable foreign keys. Both components use one migration owner; shared interface changes are coordinated before work starts.

## Ownership and bootstrap capability

Repository creation precedes a studio session, so use an explicit non-null owner capability, never an unauthenticated/null-owned staging record:

1. `POST /api/v1/studio/workspaces` creates a random opaque `workspace_id` and high-entropy bearer `workspace_token` once, returns 201 with expiry; persist only its digest and metadata. Apply global/IP and creation admission; TLS/loopback deployment controls, `Cache-Control: no-store`, no token in URL, logs or exports. Lost token means no recovery without a separately designed account system.
2. `POST /api/v1/studio/workspaces/{workspace_id}/repos` requires that workspace capability and an idempotency key. Create an owned ingestion job and snapshot in one transaction; every query joins and verifies workspace ownership. `source_kind` is `golden_curated`, `zip`, or `public_git_url`; stream ZIP to bounded temporary storage, do not run code. All user snapshots, FTS rows and file objects have non-null owner and snapshot foreign keys, never global access based on guessable IDs. Golden data is immutable shared content; workspace authorization governs access to imported/private material. Cross-owner IDs return generic 404.
3. `POST /api/v1/studio/sessions` requires workspace capability; body `{mode, posture, scenario_id, scenario_version, repo_snapshot_id?, language_mode}`. Authorize snapshot against the same workspace; require READY and matching scenario inputs. Atomically create an independent session capability and return once `{session_id, session_token, revision, expires_at}`. Store digest only. Session bearer controls its session endpoints; workspace bearer is required for workspace repo list/import/delete. Creation replay must not persist raw bearer response in plaintext: use a client-generated secret/capability with idempotent registration or an encrypted short-lived one-time delivery scheme with explicit lost-response semantics, reviewed before coding. Do not silently create another session after an uncertain response.

A session may reference one workspace; repo access checks both ownership and session association. Deleting a session must not delete a snapshot still used by another authorized session. Workspace deletion revokes all capabilities and deletes owned sessions and snapshots after durable cleanup. Define TTLs and user-visible retention before implementation. Session expiration revokes session access but does not by itself erase workspace assets unless documented; workspace expiry runs full cleanup. This owner is a local capability boundary, not identity or multi-user account authentication.

## Proposed wire contracts

All session requests use `Authorization: Bearer <session_token>`; mutations also require `X-Idempotency-Key` (8–128 characters), with JSON, status codes and error envelope compatible with current API conventions. Session creation and workspace/import operations use their specified workspace capability. Avoid credential query strings. Typical routes:

| Method and path | Input → outcome |
|---|---|
| GET `/studio/sessions/{sid}` | snapshot `{mode, posture, scenario:{id,version}, state, epoch, diagram_revision, constraints, assumptions, last_event_seq, expires_at}` |
| POST `/studio/sessions/{sid}/turns` | `{epoch, diagram_revision, text, client_turn_id}` → 202 `{turn_id, epoch, status}`; text is editable confirmed transcript |
| POST `/studio/sessions/{sid}/interrupt` | `{expected_epoch}` → atomically increments epoch, cancels work best-effort, returns new epoch |
| PUT `/studio/sessions/{sid}/diagram` | `{base_revision, nodes, edges, assumptions}` → `{revision, validation}`; stale revision returns 409 with current revision, no write |
| POST `/studio/sessions/{sid}/diagram/proposals/{id}/accept` | `{base_revision}` → atomic validated revision; discard is explicit; undo/redo creates new immutable revisions |
| GET `/studio/sessions/{sid}/events` | `Last-Event-ID` header → ordered durable SSE events with `id=sequence`, type and JSON payload; no bearer in URL; use fetch streaming if browser EventSource cannot send Authorization |
| GET `/studio/sessions/{sid}/export` and DELETE same session | scoped export; tombstone/revoke then durable cleanup status, never raw capability |
| GET `/studio/workspaces/{wid}/repos/{rid}` | owned job state, coverage/exclusions; failures sanitized |
| DELETE `/studio/workspaces/{wid}/repos/{rid}` | reject or detach referenced active sessions by documented policy; tombstone then cleanup |

All paths above are under `/api/v1`; request models enforce bounded sizes and reject unknown fields. 401 for invalid capability, 410 for authenticated expired/deleted object, 409 for stale revisions/idempotency conflict, 413 for resource limit, 422 for invalid input, 429 admission, 503 unavailable. Prevent existence leakage by not distinguishing invalid/foreign resource to an unauthorized caller. Bind idempotency to owner, method, canonical route and request digest; different body with same key returns 409.

## Transaction, events, async fencing

Create `studio_sessions`, immutable `studio_diagram_revisions`, `studio_turns`, `studio_events`, `studio_idempotency`, `studio_usage_reservations`/ledger, workspace/repo and cleanup tables with explicit owner/session FKs and indexes. Events have `UNIQUE(session_id, sequence_no)`, typed payload/version and retention bound; allocate next sequence and commit state mutation, event and idempotency outcome in a single `BEGIN IMMEDIATE` transaction. In-progress external side effects require durable reservation before dispatch and completion/uncertain state afterward. No duplicate external call after crash with uncertain outcome; return recoverable uncertainty instead of promising exactly-once delivery. Atomic unique keys and transaction boundaries, not in-process locks, govern cross-process contention. Rate-limit and validate event replay; if cursor predates retention, return resync-required and a fresh snapshot. Poll durable events for notification across processes; disconnect does not roll back committed events.

`Revision = {session_id, epoch:int, diagram_revision:int, scenario_version:str}`; each async task captures it. Check active, unexpired and matching revision before dispatch, after each await, before emitting chunks, and atomically in the transaction that publishes final output. Interrupt, deletion and superseding change increment epoch or tombstone under transaction before cancelling local tasks. A late provider response must not write content, events, cache or rubric for a stale epoch; still settle usage as committed/uncertain. CAS update `WHERE id=? AND diagram_revision=? AND epoch=? AND deleted_at IS NULL`, require exactly one row changed and insert revision/event in same transaction. Failure returns conflict; never overwrite another revision. Provider requests require timeouts, bounded response size and cancellation; cancellation cannot imply the provider incurred no usage.

## Speech and operations integration

`SpeechService._assert_current` reads DSA code version and hash, and `STTRequest`/`TTSRequest` and existing `usage_reservations` are DSA-coupled. Do not invent exercise/code identities or use gatekeeper's placeholder insertion. Refactor transport-neutral Gnani adapter, dispatcher and quota accounting behind a narrowly typed `SpeechContext(kind, owner_id, session_id, epoch, artifact_revision)` and an injected `assert_current` function. Preserve current DSA implementation and its behavior; new studio adapter must use owned studio usage rows or a properly migrated common owner ledger without weakening global daily and per-session caps. Reservation, uncertain recovery and concurrency remain durable and shared globally across modes; check epoch around REST/WS/SSE and all cache publication. Speech text for TTS comes only from authorized stored coach messages, not caller-chosen arbitrary text; transcript edits remain user-confirmed. Retention evicts studio audio only after cancellation barrier and persists retryable cleanup obligations across restart. Text remains available if provider is disabled. No live provider calls are currently authorized; later bounded genuine tests require separate authorization and exact accounting.

Extend admission path matching to workspace/session and repo operations, charging global/IP, creation, authorized workspace/session and bounded import/stream slots; invalid capabilities never charge an arbitrary victim. Inflight limit is process-local today: either retain a documented single-coordinator deployment or implement tested shared admission before multiple workers. Keep request-body streaming limits specific to ZIP rather than buffering 50 MB in generic middleware. Extend lifecycle startup/shutdown and retention sweeps explicitly for both aggregates. Tombstone first, fence work, persist obligations, delete indexed/temporary/audio data and reconcile after restart; no claims of secure deletion from backups until retention policy and backup mechanics are implemented and tested.

## Parallel implementation interfaces after gate

**Core owner:** migration coordination, workspace/session capability, studio sessions/revisions/turns/events/idempotency, admission, speech abstraction, retention and OpenAPI. **Repository owner:** ingestion, secure archive/clone, indexing, evidence/citations and repo-specific routes/services. Both agree on interfaces before changes: `authorize_workspace(wid, bearer) -> WorkspacePrincipal`, `require_snapshot(principal, snapshot_id) -> SnapshotRef`, `start_ingestion(principal, source, idempotency_key) -> IngestionJob`, `delete_snapshot(principal, snapshot_id) -> CleanupStatus`, and `resolve_evidence(principal, snapshot_id, citation) -> VerifiedEvidence | NotFound`. Repo code never owns session capabilities; core never bypasses repo authorization. Separate migrations or jointly reviewed single migration must have unique numbers and ordered integration. Contract tests exercise cross-owner denial, tombstone and restart, without depending on shared in-memory state.

## Remaining six scenario proposals and measurable checks

The detailed source supplies BR-01/02, CORE-01/02, EXP-01 and DEF-02. For the six additional launch entries use BR-03 bounded queue → distributed work queue; BR-04 heap/top-k → distributed leaderboard; CORE-03 URL shortener; CORE-04 notification fan-out; CORE-05 search/autocomplete; EXP-02 curated FastAPI event-driven webhook reference. These are concrete authoring decisions, subject to review of source-consistent scale and versioned predicates. Preserve the separately mentioned VIVA `REPO-DEF-01` defense example as a task in EXP-01, with an alias or distinct stable ID explicitly recorded; it is not a fourth repository launch map. Validate mappings before publication.

Each authored scenario carries numeric inputs with units, assumptions, explicit thresholds and alternatives. Examples: queue stability requires `arrival_rate < effective_service_rate` under the stated failure case; retry storage is `events_per_second × retry_window_seconds × bytes_per_event` adjusted for retention/replication; cache origin load is `read_rps × miss_fraction` plus defined writes, and burst coalescing explicitly models per-key fan-in; leaderboard storage is `users × bytes_per_entry × replicas`, and staleness is compared with stated bound; URL keyspace uses `alphabet_size ** key_length` against required issued IDs plus explicit collision assumptions; fan-out write rate is `event_rate × recipients_per_event`; search index refresh and capacity use declared lag and throughput. Check topology and policy through typed graph attributes, path reachability, failure-domain survival and constraint predicates, not keyword presence. Missing inputs or unmodeled guarantees yield `unknown`, never pass. Provide counterexamples and alternate valid architecture fixtures; these illustrative formulas are not verified scenario numbers.

## Mandatory acceptance for this design

Test legacy DSA API and migrations unchanged; no studio request creates a DSA session/code row; ownership/foreign access and creation-response loss; cross-process duplicate mutation/restart and uncertain provider outcomes; CAS races; SSE cursor replay, disconnect and retention; stale async results after cancel/delete; shared quotas; import SSRF/archive/secret defenses; expiration, cleanup and scoped exports; OpenAPI contracts, bounds and accessibility. Measure budgets rather than assert them. Any unresolved capability-creation recovery, multi-process admission or cleanup semantics blocks claiming production readiness.
